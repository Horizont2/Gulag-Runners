# 12 — Git для Unity-проєкту: що має бути в репозиторії

Складено після скарги «у команди немає файлів».

## Коротка відповідь

Я перевірив поточний стан репозиторію:

```
$ git ls-files | xargs git check-ignore     # відстежені файли, які ігноруються
(порожньо)
$ git status --ignored "Gulag runners"       # що ховається в проєкті
(порожньо)
```

**Зараз `.gitignore` не ховає жодного потрібного файлу.** Тобто причина не в тому, що
правила надто широкі. Нижче — чотири реальні причини, через які в команди «немає файлів»,
і як перевірити кожну.

## Причина 1: так і має бути (найчастіше)

Після клонування **немає** тек `Library/`, `Temp/`, `obj/`, `Logs/`, `UserSettings/`.
Це нормально: Unity генерує їх сама при першому відкритті проєкту. Перше відкриття довге
(імпорт усіх ассетів) — це не поломка.

**Перевірка:** колега має відкривати проєкт **через Unity Hub**, вказуючи теку
`Gulag runners/` (не корінь репозиторію!). Корінь репозиторію Unity не відкриє.

## Причина 2: `.unitypackage` не потрапляє в репозиторій

У `.gitignore` є правило `*.unitypackage` — і воно правильне, але **стріляє в ногу**, якщо
хтось кладе завантажений асет-пак у репозиторій саме як архів: такий файл git мовчки
проігнорує, і для решти команди його просто не існує.

**Як правильно:** імпортувати пак у Unity й закомітити **розпаковані** файли з `Assets/`.
Для паків з Asset Store — не комітити взагалі (заборонено ліцензією), а записати в
[CREDITS.md](../CREDITS.md), щоб кожен доставив сам. Деталі — [10-free-assets.md](10-free-assets.md).

**Перевірка:** `git check-ignore -v "шлях/до/файлу"` — покаже, яке саме правило ховає файл.

## Причина 3: `.meta`-файли не закомічені

Якщо хтось додав файли в `Assets/`, але не закомітив парні `.meta`, у решти команди
посилання в префабах і сценах поламаються — об'єкти стануть порожніми, матеріали рожевими.
Для Unity `.meta` важливіший за сам ассет.

**Перевірка:**
```bash
# файли в Assets без парного .meta
cd "Gulag runners/Assets"
find . -type f ! -name "*.meta" | while read f; do [ -f "$f.meta" ] || echo "БЕЗ META: $f"; done
```

## Причина 4: кінці рядків і бінарники

Без `.gitattributes` Windows і macOS по-різному нормалізують кінці рядків, і YAML-файли
сцен та префабів дають конфлікт на кожному рядку; бінарні ассети git намагається зливати
як текст і псує їх. Я додав `.gitattributes` у корінь — він це закриває.

> 🔴 **Git LFS поки не вмикати.** У `.gitattributes` секція LFS закоментована навмисно.
> Якщо увімкнути LFS, а в когось у команді `git-lfs` не встановлений, він отримає замість
> текстур і моделей текстові файли-заглушки на кілька рядків — і це буде рівно той симптом
> «у мене немає файлів», тільки полагодити його потім дорожче. Вмикати тільки тоді, коли
> **всі** виконали `git lfs install`.

## Що має бути в репозиторії

| Обов'язково | Ніколи |
|---|---|
| `Assets/**` — усе, разом із `*.meta` | `Library/`, `Temp/`, `obj/`, `Build/`, `Logs/` |
| `ProjectSettings/**` | `UserSettings/` |
| `Packages/manifest.json`, `Packages/packages-lock.json` | `*.csproj`, `*.sln` (Unity генерує) |
| `.gitignore`, `.gitattributes` | `*.unitypackage` (див. причину 2) |

## Два файли правил і хто за що відповідає

- **`/.gitignore`** (корінь) — правила з `**/`, працюють хоч би де лежав Unity-проєкт,
  плюс сміття ОС і IDE, плюс правило `_ThirdParty/` для ліцензій.
- **`/Gulag runners/.gitignore`** — стандартний шаблон Unity для самого проєкту.

Обидва діють одночасно; дублювання нешкідливе.

## Якщо не допомогло

Нехай колега виконає в корені репозиторію й покаже вивід:

```bash
git status --ignored --short | head -40
git check-ignore -v "Gulag runners/Assets/<файл, якого бракує>"
ls -la "Gulag runners/Assets"
```

Перша команда покаже, що ховається; друга — яке саме правило винне; третя — чи файл
взагалі доїхав. З цим я скажу точну причину за хвилину.
