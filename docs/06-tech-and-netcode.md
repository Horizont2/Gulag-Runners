# 06 — Технології і неткод

## Стек

| Шар | Вибір | Чому |
|---|---|---|
| Рушій | **Unity 6 LTS + URP** | найкращий мобільний пайплайн для 3D на телефонах, зріла збірка під Android/iOS, готовий `.gitignore` уже в репо |
| Рендер | URP, Forward+, без пост-ефектів на low-tier | бюджет 60 fps на Snapdragon 6-series |
| Фізика | **власна фіксована детермінована симуляція**, не Unity PhysX | PhysX не детермінований між платформами → ламає неткод |
| Неткод | **rollback** (GGPO-подібний) з релей-сервером | бійка 1v1 вимагає миттєвого відгуку |
| Бекенд | легкий сервер на Go/Elixir: матчмейкінг, релей, видача сіду, валідація реплеїв | дешево, горизонтально масштабується |
| Аналітика | свій івент-пайплайн (win rate vs бюджет луту — критична метрика) | баланс неможливо затюнити без цього |

Альтернатива для Unity-нетворкінгу: Photon Fusion (shared mode) або Netcode for Entities.
Обидва дають готовий rollback, але менше контролю над детермінізмом. Для 1v1 **власний
rollback на ~15 станів** — це 2–3 тижні роботи й повний контроль. Рекомендація: власний.

## Детермінована симуляція

- Фіксований крок **60 Гц**. Жодного `Time.deltaTime` у геймплейній логіці.
- **Арифметика з фіксованою точкою** (Q16.16) для позицій, швидкостей, хітбоксів.
  Жодних `float` у симуляції. Це не опція — це умова, щоб rollback працював.
- Усі рандоми — з `xoshiro128**`, засіяного сідом матчу. Жодного `UnityEngine.Random`
  у геймплеї.
- Стан раунду мусить серіалізуватись у **< 2 КБ**, щоб rollback 8 кадрів був безкоштовним.

### Що входить у стан симуляції
позиції/швидкості двох бійців, кадр анімації бою, HP/стаміна, слоти предметів + міцність,
стан кожної скрині (закрита/в процесі/відкрита + ким), активні хазарди, таймер фази,
стан RNG.

### Що НЕ входить у симуляцію
UI загадки, частинки, звук, камера, декорації. Загадка вирішується **локально** й
потрапляє в симуляцію як один детермінований івент: `OpenLock(chestId, tick)`.
Так ми не тягнемо UI-мінігру в rollback (інакше кожен відкат перезапускав би загадку — жах).

## Неткод

- **P2P через релей**, 2 гравці. Сервер не симулює гру, але тримає стрічку інпутів
  для валідації й реплеїв.
- Інпут-делей **2 кадри** (33 мс), rollback до **8 кадрів**.
- Цільова якість: грабельно до **150 мс RTT**. Вище — показуємо гравцеві попередження
  й не ставимо в матч (регіональний матчмейкінг).
- Інпут = **1 байт** (біти напрямку + 3 кнопки). 60 Гц × 1 байт × надмірність = ~2 КБ/с.
  Це безпечно навіть для мобільного інтернету.
- При обриві: 5 сек на реконект (симуляція завмирає), далі технічна поразка раунду, не матчу.

## Античит

Головна поверхня атаки — модифікований клієнт, що «відкриває» скриню, до якої не дійшов.
- Сервер зберігає стрічку інпутів і **раз на матч переграє симуляцію** (дешево: 2 КБ стану).
  Розбіжність → флаг.
- Загадка не валідується по контенту, тільки по **мінімально можливому часу**
  для згенерованої інстанції (наприклад, «Шестерні» не можна розвʼязати швидше ніж за 0.9 сек).
- Весь лут детермінований із сіду → клієнт не може «попросити» кращий предмет.
- Телеметрія на аномалії: 100% точність парирування, нульова варіація часу загадок.

## Продуктивність (бюджет на low-tier Android)

| Метрика | Бюджет |
|---|---|
| FPS | 60 (з режимом 30 для слабких/економії батареї) |
| Draw calls | ≤ 120 |
| Трикутники в кадрі | ≤ 250 К |
| Текстурна память | ≤ 160 МБ |
| Розмір білда (Android) | ≤ 180 МБ (щоб ставився по мобільній мережі) |
| Час завантаження в матч | ≤ 5 сек |
| Нагрів | термальний тест 20 хв безперервної гри без тротлінгу нижче 45 fps |

Рішення для цього: статичне батчування модулів арени, запечене освітлення
(арена не змінює світло), скінінг на GPU, LOD тільки для фонових шарів,
**нуль real-time тіней** (тіні — запечені + один blob під персонажем).

## Структура проєкту (коли почнеться код)

```
Assets/
  _Game/
    Sim/            # детермінована симуляція, нуль залежностей від UnityEngine
      Fixed/        # fixed-point математика
      Combat/
      Loot/
      Arena/        # генератор із сіду
    Net/            # rollback, транспорт, серіалізація стану
    Presentation/   # візуал, що читає стан симуляції (однобічна залежність!)
    UI/
    Puzzles/        # локальні мінігри, віддають OpenLock-івенти
  _Content/
    Biomes/Forest/Modules/
    Weapons/
Server/             # Go: матчмейкінг + релей + валідація
Tools/              # генератор арен для редактора, валідатор, балансні звіти
```

**Головне архітектурне правило:** `Sim/` не знає про `Presentation/`. Якщо симуляцію
не можна прогнати в консольному тесті без рушія — архітектура зламана.
